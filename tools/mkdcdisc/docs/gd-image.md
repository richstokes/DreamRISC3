# GD-ROM Images (.gdi)

```
# GD-ROM, inferred from the extension
mkdcdisc -e game.elf -o game.gdi
```

Unlike CDI/MDS+MDF/NRG (see [docs/cd-images.md](cd-images.md)), a GD-ROM
image is not a single container file. A `.gdi` is a small plain-text
descriptor listing one line per track (track number, LBA, control field,
sector size, filename, and a trailing offset that is always 0), alongside
one file per track written next to it. It also always builds its own
ISO9660 filesystem and `IP.BIN` internally, so there is no Layout choice and
no External ISO Mode here -- Standard Mode is the only option, and it always
produces the same fixed disc structure a real GD-ROM has.

By default mkdcdisc produces the standard 3-track shape a real GD-ROM has: a
low-density zone (the Low Density Area) with a data track carrying the
`IP0000.BIN` boot image and a short blank CDDA track, then the high-density
data track holding the ISO9660 filesystem, pinned at the fixed physical LBA
45000. The high-density boot image also carries the `TOC1` table describing
that session, as on a real Sega disc. Adding GD-DA tracks (see below) puts
more tracks in the high-density zone.

`IP0000.BIN` is not a template of its own: it is the 256-byte header of the
high-density `IP.BIN` repeated over sixteen otherwise empty sectors, which is
what a pressed disc's two zones share. Everything the console actually boots
from — the `TOC1` table, the licence screen, the bootstrap — lives in the
high-density image, which is why a `-p/--bootstrap` file of your own
contributes its header to the low-density area and nothing else.

That high-density bootstrap comes in two variants, chosen with
`--gdi-fpu-rounding`: they differ only in the SH-4 `FPSCR` rounding mode they
leave set before handing over to your executable. The default, `nearest`, is
what every earlier release shipped; `zero` is there for code that inherits the
mode rather than setting it itself (programs built against KallistiOS set it,
and are unaffected either way).

The low-density track holds its own small ISO9660 filesystem, built
around `IP0000.BIN` as its system area, carrying the 3 files a pressed
disc references from its Primary Volume Descriptor: `COPYRIGH.TXT`,
`ABSTRACT.TXT` and `BIBLIOGR.TXT`. They are generated from the disc
metadata, and `--copyright`, `--abstract` and `--biblio` replace the
contents of any of them with a file of your own. These files live in the
low-density area only, and are not reachable from the high-density
filesystem — which is how real discs do it.

Those 3 options work in every format, not just GD-ROM: the identifier
fields are plain ISO9660. Outside `-F gdi` nothing is generated by default,
so a file is only added when you ask for one.

`--gdi-disable-copyright`, `--gdi-disable-abstract` and `--gdi-disable-biblio`
go the other way, leaving one of the 3 off the disc entirely: no file is
written and its identifier field stays empty. They exist because `-F gdi` is
the one format that writes these files on its own. A MIL-CD build never
generates them, so there it is enough not to pass `--copyright` and the file
simply isn't there, whereas a GD-ROM would carry it regardless. That behaviour
is deliberate (a pressed disc sets all 3 fields, and an image meant to
look like one should keep them), so these flags are for the discs that want
their low-density area to carry only what they put there. They take
precedence over `--copyright`/`--abstract`/`--biblio`, which are then ignored
with a warning.

You can put your own content in that area too, with
`--gdi-lda-directory`, `--gdi-lda-directory-contents` and `--gdi-lda-file`
— the same distinction as `-d`, `-D` and `-f`, which keep filling the
high-density track. Since the low-density area is what a PC or an audio
CD player sees, and is not reachable from the game's own filesystem, this is
where manuals, artwork or a PC-side installer belong, not game data.

That area is a filesystem of its own, so it gets its own sort file:
`--gdi-lda-sort-file` orders it the way `-S/--sort-file` orders the
high-density one. Both take the same format (see
[docs/sort-file.md](sort-file.md)) and neither reaches into the other's tree,
which matters because the two are unrelated filesystems whose paths both start
at `/`. The three generated text files can be weighted too.

The second low-density track is the CDDA one, and it holds ~7 seconds of
generated silence by default. `--gdi-lda-cdda-track` replaces that with an
audio file of your own — a `.wav` or raw CD-DA, same formats
`-c/--cdda-track` takes:

```
mkdcdisc -e game.elf -d data/ --gdi-lda-cdda-track intro.wav -o game.gdi
```

This is the track an audio CD player reaches, so it is the usual home for a
"this disc is for the Sega Dreamcast" warning message, the way pressed discs
use it. The track's length then comes from the file rather than the default,
so it must be at least 4 seconds (Red Book's minimum, as for `-c`) and short
enough that the whole low-density area still fits below LBA 45000, where the
high-density zone starts. Both are checked before anything is built.

Data tracks are written as **raw 2352-byte Mode 1 sectors** by default --
sync, header, user data, EDC and ECC, generated via libedc exactly as on a
real disc -- because that is what real GD-ROM dumps overwhelmingly use.
Pass `--gdi-sector-size 2048` to write plain user data with no sector
framing instead. The track filenames follow the sector format, which is the
usual convention for `.gdi` sets:

| File | Contents |
| --- | --- |
| `track??.bin` | raw 2352-byte Mode 1 data |
| `track??.iso` | plain 2048-byte data (`--gdi-sector-size 2048`) |
| `track??.raw` | CD-DA audio, always 2352-byte PCM |

Give each image a directory of its own. None of those filenames carries any
part of the `.gdi`'s name, so a second build in the same directory writes over
the first one's tracks whatever the descriptor is called, and how many of them
it writes depends on the GD-DA tracks and on `--gdi-sector-size`. mkdcdisc
refuses to build into a directory that already holds a track file, naming the
ones in the way; `--allow-overwrite` goes ahead anyway.

By default the high-density track is padded out to the full physical GD-ROM
size, which puts the boot binary where real hardware expects it — ending 150
sectors before the end of the track, the run-out every data track on a
pressed disc leaves empty — but produces a ~1GB image.

`--gdi-truncate` stops the track after its contents instead, for a much
smaller image. That image is **not a standard GD-ROM**: its high-density area
ends far short of LBA 549150, describing a disc no pressed GD-ROM could be.
Whether it boots is up to whatever reads it. An ODE that takes its table of
contents from the `.gdi` accepts one; nullDC and Demul both refuse to boot a
truncated image and drop back to the BIOS menu, and boot the same disc built
without the flag. So a full-size build is the one to reach for when an
emulator is what will read the image.

Making the image *bigger* does not help: what decides it is that the
high-density area reaches the end of the zone, not how much data it holds, so a
truncated image is refused whatever its size. Sega's rules require that area to
hold at least 30 minutes, which looks like a size worth building to — it is
not, that minimum being a constraint on pressing a disc rather than on reading
an image.

A build using the flag ends with a warning naming the LBA its high-density area
stopped at, and saying the image is not standard and may not boot. `-q/--quiet`
silences it like any other advisory.

The flag also removes the capacity check, since the track is sized to whatever
it is given: a large enough disc root produces a track running *past* LBA
549150, more disc than a GD-ROM physically has, where a padded build would
have refused to build at all. mkdcdisc warns and says by how many sectors, but
still writes the image — an ODE that reads it may or may not care.

GD-ROM output builds its own ISO9660 filesystem and `IP.BIN`, so it cannot be
combined with `-t/--external-data-track`, `-L/--disc-layout`, or
`-I/--dump-iso`. It
also does its own track padding, so `-N/--disable-data-track-padding` is
rejected as well — use `--gdi-truncate` instead. A boot binary given already
scrambled (`-B/--main-binary-scrambled`) is unscrambled on the way in, since
GD-ROM boot requires an unscrambled `1ST_READ.BIN`.

See [docs/examples.md](examples.md) for more build recipes.

## GD-DA audio tracks

`-c/--cdda-track` works with `-F gdi` too, placing the audio inside the
high-density area the way a pressed disc does — between an opening data
track that holds the filesystem headers and a closing one that holds the
content:

```
mkdcdisc -e game.elf -d data/ -c music1.raw -c music2.raw -o game.gdi
```

The resulting disc has a 150-sector gap on each side of the audio block,
while consecutive audio tracks sit flush against one another with no gap at
all. The embedded `TOC1` table lists every high-density track with its own
CTRL, and the zone still closes on a data track, as every commercial GD-ROM
does.

**At most 95 audio tracks.** Sega's rules for a GD allow that many in the
high-density area, followed by another Mode 1 track, and the structure gives
the same figure: the area spans tracks 3 to 99, and the audio sits between an
opening data track and the closing one. The `TOC1` table has room for exactly
those 97 entries, so a 96th audio track would leave the TOC describing fewer
tracks than the disc has. mkdcdisc refuses the invocation instead, before
reading any of the files.

Options that only apply to this format are named with a `--gdi-` prefix, so
`mkdcdisc --help | grep gdi` lists them all.
